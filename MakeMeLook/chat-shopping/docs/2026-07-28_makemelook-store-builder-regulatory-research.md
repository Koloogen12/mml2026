## 0. Контекст и как читать этот документ

MakeMeLook рассматривает запуск продукта «собственный интернет-магазин из коробки» для продавцов/брендов (в первую очередь — уходящих с Wildberries/Ozon, у которых своего сайта ещё нет), с AI-примеркой и AI-стилистом как встроенным дифференциатором, не бонусом. Документ собирает всё, что выяснено о рыночном ландшафте, регуляторной архитектуре и технических механизмах, необходимых для проектирования такого продукта в РФ.

Каждый раздел указывает источник находки: либо прямая ссылка (URL), либо пометка «живое наблюдение» (Данил лично зарегистрировался в Яндекс KIT и снял скриншоты интерфейса — это данные более высокого доверия, чем вторичные источники).

Точная финальная архитектура MML описана в разделе 11 — если нужен только вывод, а не вся база, идите туда.

## 1. Стратегический ландшафт РФ

### 1.1 Яндекс KIT — прямой конкурент

**Что это:** новый (не переименованная «Витрина» на Яндекс.Маркете — это отдельная, более скромная вещь) конструктор интернет-магазинов, kit.yandex.ru.

**Хронология:**
- Разработка велась с закрытой бетой ~март 2025 (участники: Bazioni, «Тело-движения»)
- **Официальный публичный запуск: 8 августа 2025** — пресс-релиз самого Яндекса (первичный источник)
- Изначально доступ был ограничен категориями: одежда, красота, дом/DIY, детские товары, сад
- **Октябрь 2025 — открытый self-serve доступ всем продавцам**, без заявки/одобрения
- На сегодня (2026-07-28) — General Availability, ~11-12 месяцев с запуска

**Что бандлит:**
- No-code сайт-конструктор с SEO-оптимизированными по категории шаблонами
- Каталог, заказы, управление клиентами
- Свой домен
- Платежи + BNPL (Сплит)
- Одноклик-чекаут без регистрации покупателя
- Фискализация/налоговый комплаенс
- Логистика + хуки CRM/1С/МойСклад/склад
- AI-ассистент для настройки/аналитики (KitAI / «Альти»)
- Авто-импорт каталога продавца, уже торгующего на WB/Ozon/Яндекс.Маркете
- **Бесплатный core-тариф**; монетизация — премиум-финсервисы, реклама, доставка (не плата за хостинг магазина)

**Целевая аудитория:** независимые бренды/производители/дистрибьюторы/концепт-сторы, желающие свой магазин вне зависимости от комиссий МП — прямое пересечение с нашим целевым сегментом.

#### 1.1.1 Живые наблюдения из интерфейса KIT (Данил зарегистрировался лично, скрины 2026-07-28)

Данные ниже — из реального интерфейса `kit36378.b2b.kit.yandex.ru`, `rivael.kit.yandex.ru`, `checkout.kit.yandex.ru`, доверие выше вторичных источников.

**Онбординг-визард** — 5 шагов: Выберите дизайн → Добавьте товары → Укажите информацию о компании → Подключите доставку, оплату и онлайн-кассу → Настройте домен и подключите Яндекс Метрику → Опубликовать магазин.

**Темы завязаны на категорию продавца:** Alveria (косметика/уход Premium-сегмента), Vortelis (мебель/товары для дома), Rivael (одежда, обувь, аксессуары) — категорийная специализация с самого начала, не generic-конструктор.

**Источники товаров** (выбор при импорте): 1С, Wildberries, Ozon, МойСклад, ссылка на YML-фид, Яндекс Маркет, файл Excel.

**Оплата:**
- Featured/продвигаемый в визарде вариант — **Яндекс Пэй**, не ЮKassa/Т-Банк напрямую.
- Раздел «Онлайн-касса»: предлагает **ровно два варианта — CloudKassir и АТОЛ Онлайн**, плюс третий — «Буду использовать свою кассу» с явным предупреждением: *«Вы сможете использовать свою кассу, но чеки по заказам и возвратам нужно будет формировать вручную. Это требует больше контроля: важно не забыть и не ошибиться в сумме или данных заказа»*.
- Модалка предупреждает: «Настройка доставки и оплаты может занимать до 7 дней».

**Логистика** (вкладка «Службы доставки»): Ozon Доставка, СДЭК, ПЭК, Dalli — каждая подключается кнопкой «Подключить» с вводом своих учётных данных продавца.

**Склады:** магазин не может принимать заказы, пока не активирован хотя бы один склад — «Все склады отключены. Чтобы делать заказы, нужно активировать хотя бы один».

**Домен:** по умолчанию `https://kit36378.yastore.yandex.ru` (сгенерированный поддомен), свой домен подключается самостоятельно через DNS у любого регистратора. **Полноценного sandbox нет** — предупреждение: «Рекомендуем сделать тестовый заказ до переноса домена... Оплата и доставка товара будут реализованы в рамках реальной сделки».

**API:** раздел «Настройки → API» — реально работает, есть генерация токенов («Сгенерировать токен») и ссылка на документацию API. Это обновляет более раннюю вторичную находку («общий API анонсирован на Q4 2025, не подтверждён как выпущенный») — **на практике API уже живой**. Точный скоуп (можно ли программно создавать заказы или только читать отчёты) не проверен — следующий шаг.

**Интеграции** (отдельный от «Настроек» раздел) — закрытый курируемый Яндексом список, НЕ открытый app-store: Вебмастер, Google Search Console, Яндекс Товары, RetailCRM, Битрикс24, AmoCRM, Jivo, Admitad, Яндекс Метрика (обязательна для работы сайта). Попасть в этот список — деловые переговоры с Яндексом за место, не self-serve техническая интеграция как у inSales.

**О компании:** ИНН — обязателен технически («нужен для подключения оплаты и доставки»), автоматически подтягивается из аккаунта и валидируется («Проверьте корректность ИНН»). Публичные блоки на витрине (Телефон/Адрес/Email) — **опциональны**, у каждого свой переключатель видимости — Яндекс не принуждает к полному публичному раскрытию личности продавца.

**Форма товара:** поля — Документы (сертификаты, до 10 файлов), Категории, Артикул и штрихкод, Цена до/со скидкой, Минимальная цена, **Ставка НДС**, Остатки (простое число на склад, НЕ таблица инстансов кодов), Вес и габариты с упаковкой. **Честный Знак / код маркировки нигде не упоминается и не запрашивается как поле** — подтверждено лично проверкой формы создания товара.

**Чекаут** (`checkout.kit.yandex.ru`): физически на ОБЩЕМ поддомене Яндекса, не на домене магазина продавца (`rivael.kit.yandex.ru`) — не проверено, переезжает ли чекаут на кастомный домен после его подключения. Получатель заказа автозаполняется из Яндекс ID покупателя (единый вход по экосистеме Яндекса — преимущество, которое сложно повторить без партнёрства с крупным ID-провайдером). Есть «Поделиться заказом» (шаринг корзины). Есть привязка доставки к конкретному товару — «Нужна другая доставка... Сейчас не можем оформить этот товар» при недоступности ПВЗ для конкретной позиции.

**Карточка товара (PDP):** feature-список — «Доставим в пункты выдачи Яндекс Маркета», **«Примерьте товары и верните неподходящие»** (физическая примерка на ПВЗ, не AI), «Оплата частями в Сплит» (BNPL), **«Оплачивайте после примерки»** (pay-after-fitting), «Удобный возврат». Это отдельная, уже работающая trust-механика конкурента (примерка вживую на ПВЗ), решающая ту же проблему неуверенности в размере/посадке, что и наша AI-примерка — другим способом.

**Монетизация сверх бесплатного core:** платная managed-onboarding программа («Оптимальная» и выше) — Яндекс сам собирает магазин под продавца за отдельную плату («Поможем быстро собрать витрину для роста продаж», CTA «Подать заявку»).

### 1.2 Yandex Market Ultima — AI-примерка уже в проде (важнейший конкурентный сигнал)

**Запуск: 30 января 2026**, бета, тариф Ultima на Яндекс.Маркете (НЕ в KIT). Собственная модель — **MMDiT (Multimodal Diffusion Transformer)**, in-house разработка, не лицензированная у третьих лиц. Покупатель загружает фото в полный рост, видит одежду на себе, может дособрать образ сочетающимися вещами. Живая в 9 городах (Москва, СПб, Екатеринбург, Краснодар, Н.Новгород, Новосибирск, Ростов, Тюмень, Челябинск), исключает нижнее бельё/купальники/обувь/аксессуары.

Отдельно: QR-коды в примерочных ПВЗ Яндекс.Маркета — ведут на AI-агента, который рекомендует сочетающиеся вещи к уже заказанным.

**Вывод:** в самом KIT AI-примерки нет, но у Яндекса уже есть модель, дистрибуция (Маркет) и оргструктура под неё — перенос в KIT для них тривиальная инженерная задача, не научная. Окно нашей дифференциации реальное, но не бесконечное.

### 1.3 YCP (Yandex Commerce Protocol) — единственная открытая дверь для встройки

Протокол агентной коммерции, запущен **27 февраля 2026** — стандарт для «покупки в один клик» из диалога с AI-агентом (Алиса, Поиск, Yandex Ritm). Нативно вшит в KIT («всё уже настроено» для продавцов KIT). **Открыт третьим разработчикам в режиме беты.**

Отдельно — AI-шопинг-агент внутри Алисы (январь 2026) для чат-подбора товаров.

Общий API для глубоких интеграций (не YCP) был анонсирован TAdviser как «запланирован на Q4 2025» — **не подтверждён как выпущенный на момент того ресерча**, но живое наблюдение (раздел 1.1.1) показывает, что раздел «API» с генерацией токенов уже реально существует в интерфейсе — статус общего API нужно перепроверить напрямую по документации.

## 4. Юридический статус — «владелец агрегатора» vs «интернет-магазин»

**Это единственный по-настоящему открытый вопрос из всего ресерча — требует письменного заключения реального юриста до проектирования чекаута, не после.**

### 4.1 Точная правовая база (исправлено — не «ст. 9.1», как ошибочно фигурировало в более раннем разборе)

Нормы находятся в **преамбуле, Ст. 9 (п.1.2–1.3) и Ст. 12 (п.2.1–2.3)** Закона РФ «О защите прав потребителей», введены **250-ФЗ от 29.07.2018**, действуют с 1 января 2019. Отдельной «ст. 9.1» в тексте закона нет.

### 4.2 Определение и триггер

«Владелец агрегатора информации о товарах (услугах)» — организация/ИП, владеющая программой/сайтом, дающей потребителю **ОДНОВРЕМЕННО** возможность:
(а) ознакомиться с предложением продавца заключить договор,
(б) заключить договор купли-продажи с продавцом,
(в) **произвести предоплату ПУТЁМ ПЕРЕВОДА ДЕНЕЖНЫХ СРЕДСТВ ВЛАДЕЛЬЦУ АГРЕГАТОРА** (в рамках безналичных форм расчётов по 161-ФЗ).

**Критически важно:** пункт (в) прямо привязывает статус агрегатора к тому, что деньги получает САМА ПЛАТФОРМА. У модели MML (некастодиальная, деньги идут напрямую продавцу под его ИНН) пункт (в) не выполняется — это аргумент в нашу пользу, но не автоматическая победа (см. 4.4).

### 4.3 Обязанности и ответственность агрегатора (если бы статус применился)

- Ст. 9 п.1.2–1.3: раскрывать свои и продавца реквизиты (наименование, адрес, часы работы, ОГРН/ОГРНИП), обновлять в течение 1 рабочего дня после уведомления продавцом об изменении.
- Ст. 41: предоставлять информацию Роспотребнадзору по запросу.
- Ст. 12 п.2.1: ответственность за убытки потребителя от недостоверной/неполной информации о товаре или продавце, на которую он полагался — **но есть safe harbor**: агрегатор освобождается, если НЕ изменял информацию, предоставленную продавцом.
- Ст. 12 п.2.2–2.3: потребитель может требовать возврат предоплаты от агрегатора, если (i) товар/услуга не доставлены/не оказаны в срок И (ii) потребитель направил продавцу уведомление об отказе от договора — агрегатор может отказать, если продавец предоставил доказательство доставки в течение 10 дней; потребитель может обратиться в суд.
- По умолчанию за исполнение договора и качество товара отвечает продавец, не агрегатор (стороны могут договорно перераспределить это, как в модели Fulfillment-by-Amazon).

### 4.4 Однотенантная витрина vs мультипродавцовый маркетплейс — суть вопроса, и она реально спорная

- **Роспотребнадзор** в собственном региональном разъяснении прямо разграничивает: «интернет-магазин» — сайт, где **ОДИН продавец** предлагает товары, покупатель заключает договор напрямую с этим продавцом **без посредника**; агрегатор/маркетплейс определяется через хостинг **МНОЖЕСТВА независимых продавцов** с платформой-посредником. Это поддерживает нашу позицию.
- **НО**: юрист **М.А. Рожкова** (zakon.ru, 2018, со ссылкой на «Хозяйство и право») прямо предупреждает, что *текст самого закона* не требует множественности продавцов — там просто сказано «предложением продавца» (единственное число) — и формулировка достаточно широка, чтобы «много чего может подпадать под понятие «агрегатор»». Практик С. Лидовский в том же треде возражает, что важно не владение платформой, а то, **кто заключает договор с покупателем и кто получает деньги** — это совпадает с нашим аргументом о некастодиальности.
- **Итог:** есть два независимых, небанальных аргумента ЗА «не агрегатор» (однопродавцовая витрина по неформальному толкованию Роспотребнадзора; деньги никогда не попадают на счёт платформы согласно третьему признаку самого определения) — но ни один не является явной, судебно закреплённой нормой, и практики/прецедентов почти нет. Это именно тот тип интерпретационного пробела, который требует юридического заключения, желательно письменного, до масштабирования.

### 4.5 Как эту тему обходят существующие платформы

Прямо проверены живые оферты Тильды (tilda.cc/ru/terms/) и inSales (insales.ru/page/agreement) — **слово «агрегатор» НЕ встречается НИ В ОДНОЙ из них.** Это опровергает предположение, что стор-билдеры явно отказываются от статуса агрегатора в оферте — **они просто не поднимают тему вообще**, ни в одну, ни в другую сторону. (1С-Битрикс и CS-Cart не проверялись — считать неподтверждённым, не опровергнутым).

### 4.6 152-ФЗ (персональные данные) — второстепенный, но связанный вопрос

Для любого оператора, обрабатывающего персональные данные граждан РФ (имя/адрес/телефон для доставки), независимо от места регистрации компании: первичный **сбор** данных должен идти через базы данных, физически расположенные в России — поправка от **1 июля 2025** к Ст. 18 ч. 5 ужесточила это, убрав старую формулировку «первичная запись в РФ, затем синхронизация за рубеж». Дальнейшая обработка/трансграничная передача уже собранных данных может идти по стандартным правилам согласия/уведомления Роскомнадзора. Практический вывод: нужна RU-хостинг инфраструктура для первичного хранения ПДн с первого дня, плюс регистрация в реестре операторов Роскомнадзора до начала обработки. Правоприменение в 2025 сместилось от моратория на плановые проверки к возобновлённым внеплановым проверкам (с января 2025); конкретные суммы штрафов из вторичных источников разнятся — сверять с актуальной редакцией КоАП Ст. 13.11 отдельно, не считать settled.

## 5. Платежи — техническая специфика по провайдерам

Модель — **некастодиальная**: каждый продавец подключает свой мерчант-аккаунт/ключи, платформа только прокладывает провода, деньги никогда не проходят через MML.

### 5.1 ЮKassa (YooKassa)
- **Интеграция:** редирект на хостед-страницу, встраиваемый JS-виджет (Checkout), либо чистый server-to-server REST API.
- **Авторизация:** `shopId` + `secretKey`, HTTP Basic Auth. Тестовый режим — отдельная тестовая пара `shopId`/`secretKey` из кабинета, отдельного sandbox-домена нет.
- **Идемпотентность:** заголовок `Idempotence-Key` (рекомендуется UUIDv4), обязателен на POST-запросах; окно идемпотентности — 24 часа.
- **Вебхуки:** POST на настроенный HTTPS-URL с `{type, event, object}`. **Нет HMAC/подписи** — подлинность через (а) IP-allowlist (документированные CIDR, например 185.71.76.0/27) и (б) обязательный повторный запрос реального статуса объекта через API, не доверие телу вебхука напрямую. Нужно ответить HTTP 200, иначе повтор в течение 24ч.
- **Возвраты:** `POST /refunds` по `payment_id`, полный/частичный, в течение 3 лет с момента платежа; асинхронно, статус `succeeded` через поллинг.
- **54-ФЗ/маркировка:** объект платежа/чека принимает полные фискальные данные — `vat_code`, `payment_subject`, `payment_mode`, `measure`, и **`mark_code_info`** (`gs_1m`/`short`/`fur`) для кода Честного Знака — прямо в платёжном API, отдельная интеграция с кассой не нужна.

**Источники:** [Вебхуки](https://yookassa.ru/developers/using-api/webhooks) · [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format) · [Параметры чека 54-ФЗ](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values) · [Возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds)

### 5.2 Т-Банк эквайринг (Tinkoff Acquiring)
- **Интеграция:** хостед-редирект (Init → PaymentURL), встраиваемая JS-форма, полный server-to-server API (Init/Charge/Confirm/Cancel).
- **Авторизация:** `TerminalKey` + `Password`. Каждый запрос несёт вычисляемый `Token` (двойная роль — аутентификация и подпись per-request). Отдельный демо-`TerminalKey` для sandbox.
- **Идемпотентность:** нет глобального заголовка; идемпотентные повторы через `ExternalRequestId` на операциях типа Cancel/refund.
- **Вебхуки:** POST на `NotificationURL`. Подлинность через `Token`: собрать все корневые параметры (исключая вложенные объекты типа `Receipt`/`Data` и сам `Token`), добавить `Password`, отсортировать по ключу, конкатенировать значения, SHA-256-хэш, сравнить. Ответ HTTP 200 + тело `OK` за 10 секунд, иначе повторы (по часу 24ч, затем ежедневно месяц).
- **Возвраты:** метод `Cancel` по `PaymentId`; для статуса `AUTHORIZED` — отмена холда, для `CONFIRMED` — реальный возврат на карту.
- **54-ФЗ/маркировка:** объект `Receipt` прямо в запросах Init/Charge — `Items[]` с `Name`, `Price`, `Quantity`, `Amount`, `Tax`, `PaymentMethod`, `PaymentObject`, и поле **`MarkCode`** конкретно под код Честного Знака — нативно в платёжном API.

**Источники:** [Начало работы](https://www.tbank.ru/kassa/dev/payments/) · [Уведомления](https://developer.tbank.ru/eacq/intro/developer/notification) · [Token](https://developer.tbank.ru/eacq/intro/developer/token) · [Сценарий отмены/подтверждения](https://developer.tbank.ru/eacq/scenarios/cancel_confirm/) · [Cancel API](https://developer.tbank.ru/eacq/api/cancel)

### 5.3 CloudPayments
- **Интеграция:** встраиваемый JS-виджет (флагманский паттерн), полный server-to-server REST API, хостед-страница для простых ссылок/счетов.
- **Авторизация:** `Public ID` + `API Secret`, HTTP Basic Auth. Тестовый режим через специальные тестовые номера карт на том же API.
- **Идемпотентность:** `request_id`-подобный параметр возможен, но задокументировано менее строго, чем у ЮKassa — рекомендуется defensive-тестирование.
- **Вебхуки:** заголовки `Content-HMAC`/`X-Content-HMAC` — HMAC-SHA256 над телом запроса (URL-encoded/decoded соответственно) с использованием API Secret, base64. Это отдельная от ЮKassa/Т-Банка схема — общий код верификации не переиспользовать.
- **Возвраты:** отдельный эндпоинт возврата по ID исходной транзакции, отдельно от «отмены» (void) для неподтверждённых двухстадийных платежей.
- **54-ФЗ/маркировка:** ⚠️ **исключение из общего паттерна** — передача кода маркировки требует подключения ОТДЕЛЬНОГО продукта **CloudKassir** (своя облачная касса от того же вендора); ядро платёжного API само по себе не подтверждено как несущее поле кода маркировки, в отличие от ЮKassa/Т-Банка/Робокассы.

**Источники:** [Документация CloudPayments](https://developers.cloudpayments.ru/) · [Инструменты API](https://cloudpayments.ru/wiki/integration/instrumenti/api) · [CloudKassir](https://developers.cloudkassir.ru/)

### 5.4 Робокасса (Robokassa)
- **Интеграция:** преимущественно редирект на хостед-страницу (классический агрегаторский флоу), плюс документированный REST API и SDK для server-to-server.
- **Авторизация:** `MerchantLogin` + два пароля магазина (`Password#1` для подписи инициации платежа, `Password#2` для проверки callback Result URL). Полный sandbox через флаг `IsTest=1` на том же логине, отдельный тестовый аккаунт не нужен.
- **Идемпотентность:** нет документированного механизма ключа идемпотентности; безопасные повторы — через уникальность собственного `InvId` мерчанта.
- **Вебхуки:** callback «Result URL» с подписью `SignatureValue = MD5(OutSum:InvId:Password#2[:доп.параметры])` (можно выбрать SHA-256/384/512 вместо MD5 в настройках магазина) — merchant-вычисляемый хэш, ещё одна отдельная схема.
- **Возвраты:** отдельный Refund API по `InvId`, тестируемый в sandbox до продакшена.
- **54-ФЗ/маркировка:** JSON-параметр `Receipt` передаётся вместе с параметрами платежа (и входит в подпись) — включает `sno`, per-item `payment_object`, `payment_method`, `tax`, и объект **`mark_code_info`** (`gs_1m`/`short`/`fur`) — тот же паттерн, что у ЮKassa, нативно в платёжном API.

**Источники:** [Документация Robokassa](https://docs.robokassa.ru/) · [Тестовый режим](https://docs.robokassa.ru/testing-mode/) · [Refund API](https://docs.robokassa.ru/refund-api/) · [Фискализация](https://docs.robokassa.ru/ru/fiscalization)

### 5.5 Сравнение и рекомендация

**Эффорт по интеграции (проще→сложнее):** ЮKassa ≈ Т-Банк (оба отлично задокументированы; у ЮKassa проще всего реализовать верификацию вебхука, но она криптографически слабее IP-листом; у Т-Банка отличные доки, но токен через сортировку-конкатенацию полей возни больше) < CloudPayments (хороший HMAC, лучший UX виджета, но маркировка требует второй продукт CloudKassir) < Робокасса (функционально, но заметно более старые доки, MD5-схема по умолчанию ощущается legacy).

**Критично для архитектуры:** у всех четырёх — РАЗНЫЕ схемы проверки подлинности вебхука (IP-allowlist / конкатенация-полей-SHA-256-токен / HMAC-заголовок / MD5-подпись). **Общую функцию верификации не написать — нужен адаптер на каждого провайдера**, но верхнеуровневую модель платежа/чека/возврата унифицировать можно, т.к. три из четырёх (ЮKassa, Т-Банк, Робокасса) несут почти идентичную структуру кода маркировки нативно в платёжном API.

**Рыночная доля:** авторитетной публичной разбивки нет (цитируемые отчёты РБК/AnalyticResearchGroup — платные), но ЮKassa наиболее последовательно цитируется как дефолтная/нативная интеграция почти во всех RU e-commerce CMS (Битрикс, Тильда, inSales, WooCommerce-RU, amoCRM) благодаря наследию Сбербанка/Яндекса — ближайший аналог «инкумбента» для SMB fashion e-commerce. Т-Банк эквайринг — быстрорастущий второй благодаря агрессивному банковскому бандлу Т-Бизнеса. CloudPayments склоняется к более крупным/enterprise мерчантам. Робокасса чаще встречается у очень малых/индивидуальных продавцов и инфобизнеса, чем у fashion-ритейла конкретно.

**Решение MML:** ЮKassa + Т-Банк — пара для старта.

## 7. Честный Знак — полная база знаний

### 7.1 Категории и волны маркировки одежды/текстиля (актуально на 2026)

- **Волна 1** (2019-2021): верхняя одежда (пальто, куртки, плащи), блузки/сорочки, постельное бельё, кожаная одежда
- **Волна 2** (с 1 апреля 2024): свитеры/кардиганы, мужские сорочки, костюмы/платья/юбки/брюки, шарфы/платки, спортивная/лыжная одежда, одежда из искусственного меха/войлока/нетканых материалов
- **Волна 3** (с 1 марта 2025): нижнее бельё, чулочно-носочные изделия, купальники, головные уборы (незащитные), перчатки/варежки (непроизводственные), детская одежда, галстуки, бюстгальтеры
- **Волна 4** (с 1 марта 2026 — новейшая): спецодежда/защитная одежда, защитные каски, спасательные жилеты, кожаные ремни/аксессуары (ТН ВЭД 4203), огнестойкая спецодежда, защитные головные уборы (ТН ВЭД 6506 10), рабочие перчатки. **Продажа немаркированных остатков волны 4 запрещена с 1 августа 2026; полная маркировка остатков должна быть завершена к 1 декабря 2026.**

Обувь маркируется отдельно, обязательно с 2019 года.

Актуальный, всегда-действующий перечень — на честныйзнак.рф («Бизнесу»), проверяется по ТН ВЭД/ОКПД2, юридическая база — Распоряжение Правительства РФ №792-Р (30 товарных групп по всем отраслям, не только фэшн).

**Уверенность:** средне-высокая. Даты волн согласованы между несколькими 2025-2026 источниками (Astral, МойСклад, markirovka.ru — официальный community-сайт ЦРПТ), но прямая загрузка страницы категорий на честныйзнак.рф не удалась (только поиск) — точные списки ТН ВЭД нужно финально сверить с сайтом перед хардкодом категорий.

### 7.2 Гранулярность кода — на физическую единицу, подтверждено дважды

Каждый код Data Matrix уникален на КОНКРЕТНЫЙ физический экземпляр товара. Кодирует GTIN (14-значный, идентифицирует SKU/модель товара глобально) **плюс** уникальный серийный номер **плюс** крипто-хвост (подпись верификации, мин. 44 символа по ФФД 1.2). Два одинаковых свитера одного размера/цвета имеют одинаковый GTIN, но два разных полных Data Matrix-кода.

⚠️ **ВАЖНОЕ АРХИТЕКТУРНОЕ УТОЧНЕНИЕ (живое наблюдение перекрыло первоначальный вывод ресерча):** несмотря на то, что код уникален на физическую единицу, это **НЕ означает**, что модель данных витрины/каталога должна хранить таблицу инстансов кодов вместо простого числа остатка. Живое наблюдение интерфейса Яндекс KIT (раздел 1.1.1) показало: даже у этой продвинутой, хорошо ресурсной платформы, интегрирующей ATOL/CloudKassir (оба явно умеющие код маркировки), в форме товара — простое поле «Остатки, шт.» на склад и «Артикул и штрихкод» на уровне SKU, **никакой инстанс-гранулярности кодов в каталоге нет**. Гранулярность остаётся на уровне склада/1С/МойСклад продавца (у которых она уже нативно поддерживается — см. раздел 7.4), привязка конкретного кода к конкретной продаже происходит на кассе/складе в момент отгрузки, а не в базе данных платформы-витрины.

### 7.3 Технический механизм вывода из оборота — ДВА РАЗНЫХ режима в зависимости от канала продажи

Это самая важная техническая находка всего блока — **розница (прилавок/самовывоз) и дистанционная торговля с курьером работают по принципиально разным механизмам.**

#### 7.3.1 Режим «Розница» (прилавок, самовывоз с кассой на месте)

- **Требования к кассе:** ФФД 1.2 обязателен (1.05/1.1 не умеют нести данные маркировки) — вводит составную структуру: тег **1162** («код товара») оборачивает тег 1163 (упорядоченный набор), содержащий тег **2106** (сам DataMatrix-payload), плюс новые типы документов обмена маркировкой: «запрос о коде маркировки», «ответ на запрос», «квитанция на уведомление», и **тип документа 118** («уведомление о реализации») — фактический триггер вывода из оборота. Фискальный накопитель — должен быть ФФД-1.2-совместимым (поколение ФН-1.1М). Сканер — сертифицированный **2D-имиджер** (не обычный 1D-лазерный).
- ⚠️ **Новое требование, отсутствовавшее в первом заходе ресерча**: с **7 января 2026** (переходный период продлён до **1 июля 2026**) касса должна нести сертифицированный модуль **ТС ПИОТ** («технические средства проверки идентификации товаров») — отдельный сертифицированный компонент, выполняющий проверку валидности кода против Честного Знака ДО продажи, независимо от того, умеет ли это подключённый ОФД. После дедлайна перехода продажа маркированного товара без ТС ПИОТ — нарушение независимо от возможностей ОФД. **Нужно уточнить у CloudKassir/АТОЛ Онлайн, реализован ли этот модуль уже сейчас.** (Уверенность: средняя — недавнее регуляторное изменение 2026 года, источники вторичные блоги, не подтверждено напрямую на честныйзнак.рф.)
- **Сигнальный поток — два разных такта:**
  - **Проверка перед продажей (синхронно, доли секунды):** кассир сканирует DataMatrix → касса запрашивает Честный Знак в реальном времени → ЧЗ отвечает «код в обороте» (или отклоняет) → только после этого позиция добавляется в чек. Занимает «доли секунды», таймаут до fallback (офлайн-режим) — примерно 1.5–2 секунды.
  - **Вывод из оборота (асинхронно, после печати чека):** касса закрывает фискальный чек → генерирует «уведомление о реализации» (тип 118) → отправляет в подключённый ОФД → ОФД пересылает в ГИС МТ. Обычно почти в реальном времени (секунды-минуты), но **не является жёстким синхронным условием завершения продажи** — продажа завершается на печати чека, уведомление о выводе — downstream-релей того же канала, что и обычная передача чека в ОФД по 54-ФЗ.

#### 7.3.2 Режим «Дистанционная торговля» — для доставки сторонним перевозчиком (СДЭК/Boxberry/Почта России)

⚠️ **Это ключевой вывод для архитектуры MML.** Курьеры и службы доставки **НЕ являются участниками системы маркировки** — они логистические посредники вне регуляторного контура Честного Знака. Публичных СДЭК/Boxberry-документов о сканировании кода маркировки их курьерскими приложениями не найдено; API СДЭК (apidoc.cdek.ru) заточен на отгрузку/трекинг, не на маркировку. Практический вывод: для сторонних перевозчиков вывод из оборота происходит **выше по цепочке — на складе/кассе продавца в момент упаковки/отгрузки**, независимо от того, что происходит при финальной передаче курьером.

Механика: продавец подаёт **отдельный документ «Вывод из оборота»** с указанием причины **«Дистанционная торговля»** в личном кабинете Честного Знака (или через API/1С/МойСклад/подключённый сервис маркировки), основанный на **факте отгрузки со своего склада**, **в течение 3 РАБОЧИХ ДНЕЙ** с момента отгрузки — не привязан к моменту фактического получения покупателем. Юридическая база: Постановление Правительства РФ №860 от 05.07.2019 (упоминается moysklad.ru, markirovka.ru); один источник также цитирует ППРФ №1944 от 21.11.2023 как регулирующее текущие правила вывода в целом.

Самовывоз из ПВЗ обычно попадает под режим «Розница»-подобный (если касса самого ПВЗ выбивает чек в момент выдачи) — так работают собственные сети ПВЗ WB/Ozon. Курьерская доставка на дом и Почта России/наложенный платёж чаще попадают под режим «Дистанционная торговля» (предварительно декларируется при отгрузке), поскольку эти перевозчики не участники системы маркировки.

**Зафиксированное расхождение источников:** один источник (markirovka.ru) утверждает, что вывод происходит «при доставке покупателю, через чек при передаче», другие (moysklad.ru и правовая база) — «при отгрузке со склада, отчёт в течение 3 дней». Наша трактовка: оба верны для разных типов заказов — зависит от того, применим ли путь «чек с кодом» или путь «дистанционная торговля» к конкретному каналу выполнения заказа.

⚠️ **Практический вывод для MML: нашему чекауту НЕ нужна ни ТС ПИОТ, ни синхронная проверка кода в реальном времени — это требование для розницы/прилавка, не для e-commerce с курьерской доставкой (СДЭК), которую мы строим первой.** Задача платформы — донести до системы продавца (1С/МойСклад/SelSup), какой код ушёл в заказ; сам факт подачи документа вывода — обязанность продавца/его кассового ПО, не горит в момент оформления заказа (окно 3 рабочих дня).

### 7.4 Офлайн-сценарии и отсутствие связи с ОФД

- Общий офлайн-грейс-период по 54-ФЗ (буферизация чеков кассой, обязательная синхронизация в течение определённого окна) применяется к передаче чеков в целом, но **маркировка имеет свой, более строгий механизм поверх**: для проверки перед продажей, если онлайн-верификация не проходит, касса переключается на **«локальный модуль ЧЗ»** — локальный кэш (~30 МБ) allow/deny-списков, на сегодня ограниченный парой товарных групп (вода, БАДы) с жёсткими запретами; для остального (включая одежду) продавец/кассир совершает продажу на основе локальных данных.
- Для продавца **вообще без подключения к ОФД** (не временный сбой, а структурное отсутствие связи), обязанность вывода переходит полностью на ручную отчётность: данные о продажах подаются через **личный кабинет ЧЗ**, товар-за-товаром (агрегированная/объёмная отчётность прямо запрещена), **в течение 30 календарных дней** с даты продажи — та же цифра «до 30 дней», отмеченная в первом заходе ресерча, здесь подтверждена именно как специфичная для маркировки, не просто общий фискальный грейс-период.

### 7.5 Возвраты/реверс

- **Стандартный путь — автоматический**: кассир сканирует DataMatrix на возвращаемом товаре, пробивая чек возврата — этот чек идёт по тому же каналу ОФД→ГИС МТ, что и исходная продажа, и ЧЗ автоматически возвращает статус кода в оборот, без ручных действий в кабинете.
- **Деградированный путь**: если код/этикетка повреждена, отсутствует или нечитаема, кассир пробивает чек возврата БЕЗ кода, и продавец отдельно вручную разбирается со статусом кода в личном кабинете.
- **Возвраты дистанционной торговли** требуют явного указания причины «Дистанционная торговля» при отчётности.
- Если код был выведен через ручной документ (не через чек) — документ можно аннулировать в ЛК ЧЗ (требует, чтобы это была та же организация, что подавала документ, и чтобы это был последний документ, коснувшийся кода), либо поставщик переоформляет корректирующий УПД.
- ⚠️ **Кросс-складской возврат (посылка вернулась не туда, откуда отгружалась) — открытая, задокументированно нерешённая проблема даже у WB/Ozon** (см. 7.7). Прямого источника с решением именно для этого случая не найдено — это процедурный пробел, который придётся закрывать операционно, а не техническим решением «лучше рынка».

### 7.6 Ручные/не-POS пути вывода из оборота

ГИС МТ предоставляет документ типа **«Вывод из оборота»** и в личном кабинете, и через **True API** (`docs.crpt.ru/gismt/True_API/`), подаётся как подписанный (УКЭП) JSON-документ через единый метод создания документов. Коды причин покрывают именно не-POS случаи: розничная продажа без кассы, опт/B2B (через УПД с полем «СвВыбытияМАРК», что автоматически триггерит вывод в ГИС МТ при приёмке покупателем), использование для собственных нужд, порча/утрата/истечение срока годности (**3 рабочих дня** на отчёт), конфискация, уничтожение, подарки/образцы, госконтракт, трансграничная продажа ЕАЭС. По обработке статус кода переходит в RETIRED или WRITTEN_OFF в зависимости от документа/причины. (Уверенность: средняя — существование типа документа и таксономия причин хорошо подтверждены (Kontur, Cleverence, markirovka.ru); конкретный код типа во внутреннем API — низкая уверенность, сверять напрямую с `docs.crpt.ru/gismt/True_API/` перед интеграцией.)

### 7.7 Как это устроено у WB и Ozon (наша целевая аудитория оттуда)

**Wildberries:**
- **FBO** (fulfillment склада WB): продавец маркирует/регистрирует коды, отгружает на склад WB, подписывает УПД; **WB САМ выводит коды из оборота в момент продажи** через процесс документа «ДОП» в своём кабинете ЧЗ. Продавец в момент продажи не делает ничего; возвраты также обрабатывает WB автоматически, возвращая коды в оборот.
- **FBS** (fulfillment продавца): УПД не требуется. Продавец вносит/сканирует DataMatrix в «задание на сборку» WB по заказу, отгружает в логистику WB с обоими кодами, затем **обязан самостоятельно вывести КИЗ из оборота в личном кабинете ЧЗ в течение 3 рабочих дней** после продажи — это обязанность самого продавца, не WB. Штраф за просрочку: 1 000–10 000₽. Для возвратов по FBS продавец либо забирает на ПВЗ и сам управляет возвратом в оборот, либо возвращает на склад WB (конвертируется в FBO-подобную обработку самим WB).

**Ozon:**
- **FBO**: Ozon сам выводит коды из оборота в момент продажи — «упрощает процесс для продавца».
- **FBS/realFBS**: продавец сканирует коды при сборке, передаёт через API/интерфейс продавца при отгрузке; реестр Ozon отмечает код выведенным **после подтверждения отгрузки** (полная синхронизация ~24ч); продавец отвечает за подачу «Вывод из оборота» до/в момент передачи в сортировочный центр/ПВЗ, в течение 3 дней.
- **Реальный кейс сбоя** (форум mp-forum.ru, «Pavel Krinzh», 2024): товар физически продан через Ozon FBO, но данные маркировки так и не синхронизировались в Честный Знак/Меркурий из-за неверного кода ТН ВЭД в карточке — коды остались «в обороте» несмотря на реальные продажи, продавцу пришлось разбираться через поддержку Ozon. Показательный кейс того, как легко возникают разрывы синхронизации даже в системе устоявшегося маркетплейса.

**Практический вывод для MML:** продавцы, уходящие с WB/Ozon — вероятно, уже FBS-продавцы (это ближе всего по модели ответственности к «своему магазину»), а значит уже умеют самостоятельный флоу «вывод из оборота в течение 3 рабочих дней через ЛК/API». Наша платформа должна встроиться в их существующую привычку (тот же коннектор — SelSup/1С/МойСклад), а не изобретать новый процесс.

### 7.8 Реальное ПО, которое это делает у брендов/магазинов

**Для обычной розницы вне маркетплейсов:**
- **1С:Розница 8** — доминирующий ответ именно для одежды: отдельный путь настройки (НСИ и Администрирование → Интеграция с ИС МП: обувь, одежда, табак), авто-генерация приёмных ЭДО-накладных с данными кода, при продаже кассир сканирует DataMatrix, код валидируется и автоматически выводится из оборота. Самый цитируемый «стандарт» для тех, кто уже на 1С.
- **1С:УНФ (Управление нашей фирмой)** — та же конфигурация маркировки, что и 1С:Розница, для малого/среднего продавца одежды.
- **СБИС/Saby Розница** — отдельная продуктовая линия «Маркировка одежды и текстиля», позиционируется от одиночного магазина до сети, отзывы практиков — установка «за полчаса», без обучения.
- **Эвотор** — отдельное приложение «Маркировка» в своём app store, устанавливается на терминал, требует 2D-сканер (1D не читает DataMatrix), явно перечисляет одежду/обувь среди поддерживаемых категорий, приёмка и подписание ЭДО-документов встроены.
- **Set Retail 10** (модуль «Set Mark») и **Frontpad** — оба подтверждают совместимость с кодом маркировки на кассе, но без явных кейсов именно для одежды — читаются как generic мультикатегорийная поддержка, не стандарт fashion-ритейла.
- **r_keeper** — явных доказательств одёжного модуля маркировки не найдено (ориентирован на HoReCa, маркировка там больше про алкоголь/табак) — не подтверждён как стандарт для одежды.

**Отдельное ПО управления маркировкой (не кассовое):**
- **Контур.Маркировка** (SKB Kontur) — для производителей/импортёров/оптовиков/розницы; базовый тариф розница/опт ~12 000₽/год (тариф производитель/импортёр ~40 000₽/год), встраивается в интерфейс 1С модулем, а не заменяет его. Явное ограничение: базовый тариф покрывает учёт/вывод кодов, но НЕ сам заказ кодов.
- **СБИС Маркировка** — от ~2 300₽, позиционируется как full-service (помогает описать остатки, печатать этикетки, заполнять карточку товара; для производителей — помощь с GS1/GTIN), поддержка 24/7 по отзывам.
- **⭐ SelSup** — специализированная платформа операций именно для продавцов маркетплейсов (не accounting-first): генерирует коды, печатает КИЗ+штрихкод на одной этикетке, пушит коды маркировки прямо в FBS-заказы, автоматически пересчитывает остатки комплектов/наборов. Позиционируется как официальный партнёр маркетплейсов и Честного Знака по API, не скрейпинг. **Наиболее релевантен именно нашей целевой аудитории (продавцы WB/Ozon).**
- **1С:Маркировка** как отдельный продукт по сути просто означает «модуль, который включается внутри 1С:Предприятие/УНФ/Розница после установки» — не отдельная продуктовая линия, как у Kontur или СБИС.
- «Артикс:Маркировка» и «Мультибренд» — сильных подтверждений массового использования практиками не найдено.

**Реальный опыт продавцов (боль):**
- Живой кейс с vc.ru: **«Я потерял 300 000₽ из-за ошибок в маркировке Честный знак»** — описывает каскадный сбой: коды не были правильно зарегистрированы в системе ЧЗ, DataMatrix-коды не совпадали с реальными товарами в карточках, не было шага сверки при приёмке на склад перед отгрузкой — итог: ~300 000₽ товара невозможно было продавать почти три недели после блокировки карточек маркетплейсом. Цитата продавца: *«Товар на складе. Деньги вложены. А продавать ты не можешь.»* Его собственный вывод — нужен был непробиваемый шаг верификации при приёмке, а не просто лучший софт.
- Oborot.ru регулярно освещает продавцов, не успевающих к дедлайнам маркировки (например, дедлайн 1 июля для одежды) — паттерн скорее «дедлайн-лихорадка», чем гладкая работа инструментов.
- Общий паттерн по материалам о проблемах маркировки: выцветшие/повреждённые DataMatrix-коды становятся нечитаемыми (товар формально «немаркирован», даже физически присутствуя), рассинхрон остатков, когда ЧЗ всё ещё показывает товар «на складе» спустя долгое время после того, как он у покупателя — структурный разрыв между физическим выполнением заказа и состоянием реестра ЧЗ, который ни один инструмент полностью не закрывает.

**Рабочий вывод МойСклад в деталях:** документы поддержки описывают полноценный замкнутый цикл: поставщик присылает коды через ЭДО → продавец создаёт приёмку в МойСклад, сканирует/сверяет коды при приёмке, электронно подписывает УПД → коды привязываются к конкретным единицам инвентаря (учёт на уровне партии/единицы) → этикетки с кодами печатаются прямо из приложения (цикл заказ-кода-до-печати занимает 5–7 минут) → при продаже через подключённый онлайн-магазин (Тильда/inSales указаны как поддерживаемые) — точный механизм real-time запроса «какой код доступен к продаже» не раскрыт в проверенных доках, это в более глубоких интеграционных статьях. МойСклад также предлагает **офлайн/локальный модуль Честного Знака** для валидации кода на кассах без живого интернета, для сетей, нуждающихся в устойчивости на кассе.

**Что «стандарт» для малого-среднего продавца одежды сегодня:** три имени всплывают чаще всего — **1С (Розница/УНФ)** для тех, кто уже на 1С, **МойСклад** для более бюджетных небольших магазинов с лёгким облачным инструментом, **СБИС** как turnkey-вариант с поддержкой из коробки. **Контур.Маркировка** читается скорее как enterprise/опт-импортёрский вариант (тяжелее годовая плата, без встроенного заказа кодов), не дефолт малого магазина. **SelSup** — выделяется именно для продавцов маркетплейсов (WB/Ozon), не для физической розницы. Приложение Эвотора занимает ту же нишу, что 1С/СБИС, но именно для тех, кто на оборудовании Эвотора.

### 7.9 Штрафы и риски правоприменения

Под **КоАП РФ ст. 15.12** (оборот немаркированных товаров): физлица/ИП — штраф + конфискация; должностные лица — 5 000–10 000₽ + конфискация; **юрлица — 50 000–300 000₽ + конфискация ВСЕЙ партии**, независимо от категории или тяжести. На 2026 год ЦРПТ разворачивает **автоматическую выдачу штрафов** прямо по данным ГИС МТ (без визита инспектора) — повышая реальную частоту правоприменения. Масштабный оборот немаркированного товара может эскалировать до **уголовной ответственности по ст. 171.1 УК РФ** (штраф до 300 000₽ или лишение свободы до 3 лет).

Это ответственность продавца/юрлица как «участника оборота», НЕ платформы — пока платформа сама не становится таким участником.

## 8. Логистика — провайдеры с сетью ПВЗ

Модель — та же некастодиальная: продавец подключает свой аккаунт к перевозчику, платформа только прокладывает провода.

### 8.1 СДЭК (CDEK) — рекомендованный первый выбор
- **API:** документированный REST v2.0 (apidoc.cdek.ru / api-docs.cdek.ru) — регистрация заказа (`orders`), расчёт стоимости/сроков (`calculator/tariff`, `calculator/tarifflist`), список ПВЗ/постаматов с фильтрами по городу/индексу/типу, координатами, адресом, часами работы. Есть официальный JS-виджет карты ПВЗ.
- **Модель аккаунта:** подписанный договор на юрлицо → `Account` + `Secure password` (используются как OAuth2 `client_id`/`client_secret`). Готовые модули СДЭК для Битрикс, inSales, Тильда, WordPress следуют одному паттерну: модуль от платформы, но каждый владелец магазина получает и вводит СВОЙ Account/API-ключ от СДЭК (у inSales — запрос на integrator@cdek.ru, ~1 рабочий день). Модуль для Битрикс поддерживает несколько аккаунтов на одну установку. Единого «мастер-ключа на всех продавцов» режима для обычного создания заказов нет — это тот же паттерн, что и у нас с платежами/кассой.
- **Авторизация/sandbox:** OAuth2 `client_credentials` на `api.cdek.ru/v2/oauth/token`. Полноценный sandbox на `api.edu.cdek.ru`/`integration.edu.cdek.ru` с тестовыми кредами в доках.
- **Эффорт:** первая интеграция (калькулятор + список ПВЗ + создание заказа) — ~1-2 недели, готовые SDK (PHP: `AntistressStore/cdek-sdk-v2`, `appwilio/cdek-sdk`; Go: `riizeron/cdek-go-sdk`). Онбординг продавца гейтится в основном оборотом договора/ключа у СДЭК (~1 рабочий день).

### 8.2 Boxberry — НЕ рассматривать сейчас
- Исторически была своя REST API (`api.boxberry.ru`) с ПВЗ-листом, тарифами, созданием заказа, трекингом, курьерским забором, JS-виджетом карты.
- **Апрель 2025 — Яндекс купил Boxberry целиком**, интеграция сливается в Yandex Delivery, справочные страницы (help.boxberry.ru) уже редиректят на доки поддержки Yandex Delivery, которые явно предупреждают интеграторов «пересмотреть отличия API после перехода на Yandex Delivery».
- Модель аккаунта та же (свой токен из личного кабинета продавца), но документация сейчас движущаяся цель — писать код под сегодняшний Boxberry API рискованно.

### 8.3 Альтернативы на будущее
- **Yandex Delivery напрямую** — документирует ту же per-seller модель «через API» в личном кабинете, поглотит сеть Boxberry (~14 000+ ПВЗ) в любом случае — возможно, более future-proof цель, чем сам Boxberry.
- **5Post (X5, ~20 500 ПВЗ/постаматов)** — хорошо задокументированный API/виджет, per-seller API-ключ, быстрый онбординг через агрегаторы вроде ApiShip.
- **Почта России** — обычно самый неповоротливый API/EDI из группы, низкий приоритет для v1.
- **ApiShip (агрегатор)** — единый внутренний API поверх СДЭК/Boxberry/5Post, каждый продавец всё равно владеет своим аккаунтом перевозчика; возможный шорткат ценой дополнительной вендорской зависимости.

**Решение MML:** СДЭК первым.

## 9. Товароучёт — 1С и МойСклад

- **МойСклад** — официальная нативная поддержка маркировки с чистым API. Реальный рабочий цикл: поставщик шлёт коды через ЭДО → приёмка с сверкой кодов → подписание УПД → привязка кодов к единицам инвентаря (учёт на уровне партии/единицы) → печать этикеток прямо из приложения (5-7 минут цикл) → интеграция с Тильдой/inSales подтверждена как поддерживаемая. Есть офлайн/локальный модуль ЧЗ для валидации на кассах без интернета.
- **1С** — по запросу, НЕ из коробки. Экосистема фрагментирована по конфигурациям (Розница/УНФ/Управление торговлей и т.д.), единого публичного API нет ни у кого на рынке — только платные кастомные интеграции через агентства (например, cetera.ru, использующие протокол обмена ML Commerce), или встроенные модули внутри самих конфигураций 1С (см. раздел 7.8).
- **SelSup** — приоритетный кандидат специально для нашей аудитории (бывшие продавцы WB/Ozon), см. раздел 7.8.

## 11. Итоговое архитектурное решение MML (свод)

**Целевой сценарий:** продавцы, которые сейчас ТОЛЬКО на WB/Ozon (своего магазина нет вообще) и хотят уйти. Одна админка MML → выбор: виджет примерки / виджет стилиста / полный пакет интернет-магазина. В полном пакете — визард: тема → лого → импорт товаров → подключение СВОИХ кредов (эквайринг/касса/логистика/учёт) → публикация. Архитектура некастодиальная, как у Тильды: деньги идут напрямую продавцу под его ИНН, MML не платёжный агент.

**Технический стек v1 (сужен намеренно — не копировать широту Яндекса):**
1. **Платежи:** ЮKassa + Т-Банк, адаптер на каждого (разные схемы вебхуков).
2. **Касса/ОФД:** Ferma (ОФД.ру) или CloudKassir первыми, АТОЛ Онлайн вторым.
3. **Товароучёт/маркировка:** МойСклад + SelSup (приоритет для аудитории с WB/Ozon), 1С — по запросу.
4. **Логистика:** СДЭК первым, Boxberry — не сейчас.
5. **Модель данных:** остаток — простое число на SKU (НЕ таблица инстансов кодов, см. раздел 7.2), поле НДС на позицию, поле кода маркировки — опционально прокидывается в заказ для передачи подключённой системе продавца, не хранится/управляется нами.
6. **Комплаенс-модель по маркировке:** для e-commerce с курьером (СДЭК) — режим «Дистанционная торговля», не требует синхронной проверки на кассе/ТС ПИОТ, окно 3 рабочих дня на подачу документа продавцом/его системой (см. раздел 7.3.2).

**Единственный по-настоящему открытый вопрос — юридический (раздел 4):** статус «владелец агрегатора» требует письменного заключения реального юриста ДО архитектуры чекаута.

**Стратегический контекст:** Яндекс (KIT + Ultima-примерка + YCP + Boxberry) вертикально собирает весь стек. Окно AI-дифференциации реальное (в KIT примерки нет), но не бесконечное.

**Решение:**
1. Сузить v1-инфраструктуру до минимума выше — освободившееся время в AI-слой (примерка+стилист+персонализация).
2. Юридическое заключение по агрегаторскому статусу — до проектирования чекаута.
3. Параллельно прощупать YCP техническим прототипом как возможный более дешёвый путь встройки в экосистему Яндекса вместо полной конкуренции.

**Открытые технические вопросы, требующие проверки:**
- Точный скоуп API Яндекс KIT (создание заказов программно vs только чтение) — есть живой раздел в UI, документация не изучена.
- Реализован ли модуль ТС ПИОТ уже сейчас у CloudKassir/АТОЛ Онлайн (требование действует с 1 июля 2026).
- Переезжает ли чекаут KIT на кастомный домен продавца после его подключения, или остаётся на `checkout.kit.yandex.ru` навсегда.
