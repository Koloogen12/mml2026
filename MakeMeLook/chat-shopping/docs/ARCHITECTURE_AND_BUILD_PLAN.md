## 0. Что изменилось по итогам разведки

Три факта, установленные фактически, а не по памяти. Каждый меняет план.

**Git был не источником правды.** На проде лежало ~1500 строк Go и 7 миграций, которых не было в git нигде: провайдер CometAPI, провайдер Fal, роутер моделей по числу вещей, kill-switch, журнал синхронизаций, Telegram-нотификатор. `git pull` на сервере стёр бы всё это. **Устранено:** коммит `c33b56b`, 62 файла, 4903 строки. Сборка и тесты зелёные. Дальше работаем от git.

**Движок примерки в платформу не переносится — платформа его интегрирует.** Виджет уже мультитенантный, с доменной верификацией, сессиями и HTTP-API. Платформа становится в нём **проектом** — ровно как demo.makemelook.tech, где это работает на 591 товаре. Ноль общего кода, ноль общих зависимостей, ноль риска для платящего клиента.

**Дизайн покрывает все три контура,** включая девять экранов админки. Дизайн больше не блокер нигде. Но он **не источник правды для разметки** (см. §7).

## 1. Границы систем

Два продукта. Разные жизненные циклы, разные базы, разные деплои. Связь одна — HTTP-контракт.

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  ВИДЖЕТ (существует, живой) │        │  ПЛАТФОРМА (строим)          │
│  mml-saas-backend           │        │  mml-platform-backend        │
│  БД: makemelook_saas_2      │        │  БД: mml_platform (новая)    │
│  Клиенты: malinabonita и др.│        │  Пользователь: покупатель    │
│                             │        │                              │
│  Умеет: примерка (4 провай- │◄───────┤  Вызывает как обычный        │
│  дера, роутер), каталог      │  HTTP  │  заказчик: свой project_id,  │
│  проекта, лиды, согласия     │        │  свой домен, свои товары     │
└─────────────────────────────┘        └──────────────────────────────┘
        НЕ ТРОГАЕМ в фазах 0–5                   всё новое
```

**Правило, нарушение которого — инцидент:** платформа не импортирует ни одного пакета из `mml-saas-backend` и не ходит в его базу. Только публичный API виджета.

### Контракт с виджетом (спроектировать первым — от него зависит фаза 4)

| Что | Как |
|---|---|
| Регистрация платформы | Проект в виджете + `project_domain` = домен платформы |
| Каталог | Платформа пушит товары в проект виджета (как e-commerce sync). Товар в платформе ↔ товар в виджете по внешнему id |
| Покупатель | Платформенный пользователь ↔ `Lead` виджета, 1:1, маппинг хранит платформа |
| Фото | Загружается в виджет (там же и живёт биометрия) |
| Примерка | `POST /sessions/{token}/tryon` → 202 → поллинг статуса. **UI рисуем свой** — по хендоффу, а не виджетовый |
| Согласие 152-ФЗ | Записывается **в обеих** системах: в платформе (владеет отношениями с пользователем), в виджете (владеет биометрией) |

**Открытый вопрос к решению в фазе 0:** серверный API-ключ вместо сессионного токена. Сессии виджета рассчитаны на браузер с доменной верификацией; платформе нужен серверный вызов. Это маленькое добавление **в виджет** — единственное касание его кода за весь план, и делать его надо осознанно, отдельным релизом.

## 2. Стек платформы

| Слой | Решение | Почему |
|---|---|---|
| Backend | **Go 1.25 + chi + GORM + Postgres 16** | Тот же стек, что у виджета — знаем его, инструменты общие. Модульный монолит |
| Векторный поиск | **pgvector** в той же БД | Не заводим отдельное хранилище, пока не упрёмся |
| Инференс | **Python-сайдкар** (`mml-reco`): FashionCLIP, реранкер | Уже начат (`passport/body.py`, `color.py`). Go туда по HTTP |
| Объекты | **MinIO** (существующий, новый бакет) | Стоит, работает |
| LLM | **Провайдер-абстракция** + CometAPI + фолбэк | Провайдерный слой уже есть в виджете как образец; текстового клиента нет — пишем |
| Стриминг | **SSE** | В виджете стриминга нет вообще. С нуля |
| Frontend | **React 19 + Vite + TS + Tailwind v4 + Zustand** | Стек виджета. Три приложения + общий пакет UI, pnpm workspace |
| Очереди | Postgres-таблица + воркер | Не тащим Redis/Kafka, пока объём не потребует |

**Чего сознательно НЕ берём сейчас:** Kubernetes, Kafka, отдельный сервис-меш, микросервисы. Один бинарник + сайдкар + Postgres. Всё это добавляется, когда упрёмся, а не заранее.

## 3. Модель данных — три решения, которые дорого менять потом

**Товар и оффер — разные сущности.** Канон прямо требует мультиретейлерную карточку («Nordstrom $1,650 ↗ / Saks $1,650 ↗»). Значит:

```
Brand ─┬─ Product (канонический предмет: название, категория, атрибуты, эмбеддинг)
       └─ Offer  (retailer, цена, старая цена, наличие, размеры, deeplink, CPA-сеть)
```
Один товар — много офферов. Модель «товар = магазин» ломает и карточку, и экономику.

**Паспорт стиля — три слоя по скорости изменения** (из [исследования](./STYLE_PASSPORT_AND_RECS.md)):
`user_traits` (внешность, тело, колориметрия — стабильны) · `user_preferences` (вкус, бренды, бюджет — медленно, SCD-2) · `context_events` (повод, погода, настроение, сессия — быстро).
Смешивать их в одну таблицу — потерять возможность считать «сейчас» отдельно от «вообще».

**Честность уровней.** Замеряемое (пропорции тела, CIE Lab кожи, контраст) правит движком. Типологии (цветотип, Kibbe) — **только редактируемые ярлыки в UI**, в движок не идут.

## 4. Фазы

Порядок продиктован зависимостями, а не удобством. Внутри фазы бэкенд и фронт идут параллельно.

### Ф0 · Фундамент — до единой строки продуктового кода

| Задача | Результат |
|---|---|
| Решения-блокеры (§8) | Закрыты. Без них фазы 1–4 встанут посередине |
| Монорепо, workspace, CI (lint, test, build), окружения dev/stage/prod | Пайплайн зелёный на пустом проекте |
| **Дизайн-система в код** | Токены §1 аудита → CSS-переменные + Tailwind-конфиг. **Своя типографическая шкала** (12.5/13.5/11.5 — дефолты Tailwind огрубят дизайн) |
| Шрифты | Кириллический дисплей-сериф, WOFF2, `unicode-range`, `font-display:swap` |
| Моторика + `prefers-reduced-motion` | Глобальный guard **до** того, как появятся 200 анимаций |
| Иконсет | Сохранить метафоры: ✦ искра (маркер ИИ) и «фигура + искра» (примерка) — брендовые, generic-набор их убьёт |
| Контракт с виджетом | Спроектирован и согласован (§1) |
| Скелет БД + миграции + сидер | Каталог заливается из дампа (~3500 реальных товаров) для разработки |

**Выход Ф0:** можно верстать и можно писать эндпоинты.

### Ф1 · Каталог и подбор — бэкбон

Без товаров не работает ничего. Это самая недооценённая фаза.

- **Модель:** Brand / Product / Offer / ProductImage / атрибуты / таксономия из 5 гардеробных зон.
- **Ингест:** парсер витрины по URL (OG → schema.org → LLM-фолбэк) · YML/XML-фид · CSV · API. Журнал синхронизаций и **причины отказа в человеческих словах** (в кабинете уже описаны: «Фото на манекене», «Обувь пока не поддерживается»).
- **Обогащение LLM:** силуэт, вырез, повод, ткань — из фото и описания.
- **Эмбеддинги:** FashionCLIP (фото + текст) → pgvector, ANN-индекс.
- **Retrieval API:** запрос → эмбеддинг → ANN → жёсткие фильтры (размер, наличие, цена) → кандидаты.
- **Пригодность к примерке:** гейт по 5 зонам, с причиной. Это то, что защищает нас от плохих рендеров.

**Проверка на выходе:** «покажи чёрное платье до колена до 8000₽» возвращает осмысленные товары из реального каталога. Без чата, курлом.

### Ф2 · Личность покупателя — параллельно Ф1

- **Авторизация по телефону + SMS-код.** В виджете SMS **не реализован**, а коды пишутся в логи открытым текстом. Пишем с нуля, нормально: провайдер, троттлинг, коды не логируются.
- **Онбординг (6 шагов)** — имя/пол → образ жизни → стиль-пресеты → бренды → размеры/бюджет → авторизация. Паспорт собирается **до** регистрации и мёржится при входе.
- **Паспорт стиля** — три слоя (§3), редактируемый.

### Ф3 · Чат — поверхность продукта

- **Оркестратор:** разбор намерения → tool-calling (`search` / `refine` / `try_on` / `similar`) → сборка ответа → **SSE-стриминг**.
- **Заметка стилиста «почему вам»** — наше отличие от Daydream, идёт в выдачу.
- **Фронт:** home с печатающимся плейсхолдером, тред, стриминг, скелетоны, «Выбор стилиста» по умолчанию, карусель/сетка, быстрые чипы уточнения, поповер на карточке.
- Тон ответов ассистента — из `intentFor()` хендоффа: это **утверждённая копирайтерская работа**, не выдумывать заново.

### Ф4 · Примерка и 152-ФЗ — дифференциатор

- **Интеграция с виджетом** по контракту §1.
- **Согласие:** блокирующий гейт до первой примерки, **раздельные непреселекченные** чекбоксы, версия и дата с сервера (не хардкод).
- **⚠️ Панель управления согласиями и удаление данных в один тап — В ДИЗАЙНЕ ОТСУТСТВУЕТ.** UI обещает («Удалите фото и биометрию в один тап»), строка в паспорте есть, а ведёт она на блокирующий гейт. **Пункта назначения нет.** Это не полировка — это 152-ФЗ. Нарисовать в Ф0, реализовать здесь.
- Прогресс с оптимистичным UI, **сворачивание в очередь + пуш** (в макете уже описано посекундно), результат с «до/после», edge-кейсы.

### Ф5 · Покупка и атрибуция — деньги

- Карточка товара с мультиретейлером.
- **CPA-редирект:** сервис `/r/`, подписанный `click_id`, интерстишл, обработка недоступного магазина.
- **Атрибуция по каждому заказу** — то, чем мы бьём партнёрские сети. Токен сессии примерки доезжает до заказа партнёра.
- S2S-postback от сети, статусы конверсий.

### Ф6 · Кабинет партнёра

По [спеке](./PARTNER_CABINET_SPEC.md) и дизайну. Герой — витрина бренда, а не дашборд. Вход через один товар.

### Ф7 · Админка

По [спеке](./ADMIN_PANEL_SPEC.md) и дизайну. Стол стилиста здесь — **инструмент разметки для обучения моделей** (gold-set), а не способ доводить людей до покупки руками.

### Сквозное, не откладывать

Семантическая вёрстка и доступность **с первого компонента** (в макетах 1 `<button>` на 9 файлов — ретрофит стоит десятикратно) · состояния «офлайн» и «ошибка» (в B2C-прототипе их нет вообще) · наблюдаемость · антифрод по кликам · rate-limit **не в памяти процесса** (у виджета он в памяти — на второй реплике молча удвоится).

## 7. Что в хендоффе неверно — и не должно попасть в код

Дизайн высокого качества, но макеты — **пиксели, а не разметка**. Проверено фактически:

| Находка | Следствие |
|---|---|
| **Дисплей-сериф без кириллицы** (66 глифов, латиница) | Весь русский сериф — это Georgia. Дизайн, который задумывался, никто не видел. **Блокер Ф0** |
| Документация ≠ код: акцент `#2B2BCC` (не `#2743E3`), ивори `#F4F1EA` (не `#F6F4EF`), Inter (не Golos) | Верить коду. Канон устарел |
| **Три разных синих** (`#2B2BCC` / `#2436D8` / `#2E16CB`) и четыре разных «чёрных» | Унифицировать в Ф0 |
| Адаптив сделан хаками по подстроке инлайн-стиля (`[style*="repeat(4,1fr)"]`) | В React **молча перестанет работать**, без единой ошибки. Переписывать с нуля |
| «У каждого экрана 7 состояний» | **Неправда.** «Офлайн» — ноль вхождений во всех 9 файлах. У главного B2C-прототипа **нет ни одного состояния ошибки** |
| Эталонная матрица состояний «6d» | В пакете отсутствует |
| Экран «Коллекции» отрисован, но **недостижим** (`screen:'collections'` не выставляется нигде) | Решить: он или под-вкладка в Избранном |
| Мобильная навигация (плавающая пилюля из 4 вкладок) | **Не нарисована.** В прототипе десктопный топбар |
| Доступность | 1 `<button>` на 9 файлов, `alt` в B2C — ноль, `prefers-reduced-motion` — ноль при вечно крутящихся градиентах |

## 9. Порядок первых шагов

1. Закрыть B1–B4 (остальное можно на ходу).
2. Ф0: монорепо, CI, токены, шрифты, контракт с виджетом, панель согласий в дизайне.
3. Ф1 бэкенд + Ф2 фронт — параллельно.
4. Дальше по §5.

**Правило, которое держим весь проект:** не строим следующий слой, пока предыдущий не проверен запросом, который можно выполнить руками. Каталог проверяется курлом до чата. Чат проверяется до примерки. Примерка проверяется до денег.
